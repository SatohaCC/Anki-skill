# Ankiカードの類似・重複監査と整合性整理

`output/` に出力されたAnkiインポートTXT（一問一答・4択）を分析し、過剰な重複問題、章間での重複、形式間のカード枚数のズレ、設問文の競合を監査し、既存GUIDを保ったまま整理・明確化する。

## 教材フォルダの読み取り先と出力先

リポジトリの`target-folder/`直下に試験ごとのフォルダがある場合、選択した試験フォルダ（`target-folder/<試験slug>/`）を基準に標準構成を使う。

- 監査対象：`output/` 内の `<試験slug>_<章・範囲>_<一問一答または4択>_<タイムスタンプ>_Anki.txt`
- バックアップ退避先：リポジトリルートの `.local-history/`（Git管理外）
- 出力先：`output/` 内に最新のタイムスタンプを付与して保存

各フォルダ名やファイル名は、すべて試験フォルダまたはリポジトリルートからの相対パスで扱う。マシン固有の絶対パス、ユーザー名、ホームディレクトリを含めない。

## 類似・重複監査の5大基準

監査時は次の5つの観点からカードを精査する：

1. **形式間のカード枚数・対応ズレ（Format Parity）**
   - 同一範囲の「一問一答」と「4択」でカード枚数が完全一致しているか確認する。
   - 1問ずつの設問テーマを照合し、途中でカードがスキップ・欠落して以降の番号がオフセットしていないか検知する。

2. **同一正解・概念のクラスタリング（Concept Clustering）**
   - 解答の主要用語（例：「RAG」「ファインチューニング」など）ごとにカードをグループ化する。
   - 同一用語が短区間に多数出現し、設問文が単なる言い換えになっていないか検知する。

3. **設問テキストの類似度・言い換え重複（Stem Similarity）**
   - 設問文から選択肢用定型文（`（1つ選択）`、`として正しいものを...` など）やHTMLを除去した上で、文字N-gram Jaccard類似度やSequenceMatcher比を計算する。
   - 類似度が高い（目安：0.65以上）ペアを抽出し、同一の知識を冗長に問うていないか精査する。

4. **設問の競合・混乱リスク（Conflicting Questions）**
   - 問いのシチュエーションがほぼ同一であるにもかかわらず、カードによって異なる用語を正解としている箇所を検知する（例：「ベクトル比較でそろえるもの」に対して「次元」と答えるカードと「モデル」と答えるカードの混在など）。
   - 学習者が暗記時に迷わないよう、数学的性質か実装選定かの切り分けを要する箇所を特定する。

5. **章間重複（Cross-Chapter Overlaps）**
   - 異なる章（例：15-21 と 22-27）の間で、まったく同一の基本概念（例：「推論の定義」「リアルタイム推論とバッチ推論」「AIの基本定義」など）が重複して出題されていないか確認する。

## 監査スクリプトの活用

手動解析に加え、付属の監査スクリプトを実行して客観的指標を素早く取得する：

```bash
uv run python .agents/skills/anki-card-dedup/scripts/audit_cards.py target-folder/<試験slug>/output
```

JSONレポートが必要な場合：
```bash
uv run python .agents/skills/anki-card-dedup/scripts/audit_cards.py target-folder/<試験slug>/output --json <出力パス>.json
```

## 整理・改善の実施手順

監査結果に基づき、以下の手順でカードの修正・整理を行う：

1. **方針の確定**
   - 重複カードを削除・統合して枚数を減らすか、復習用として残しつつ設問の角度を分けるかをユーザーと確認・合意する。

2. **設問の差別化・明確化**
   - 似た概念が並ぶ場合は、各カードの出題意図を明確に差別化する：
     - **基本定義**: その技術・概念が何であるか
     - **アーキテクチャ・手法選定**: いつその手法を選ぶか（他手法との対比）
     - **特定課題の解決**: ハルシネーション対策、セキュリティ、コスト最適化など特定の目的に対する役割
     - **数学的性質 vs システム選定**: 「ベクトルの次元数」と「共通の埋め込みモデル」のように、問う階層を明記する

3. **Anki GUIDの厳格な維持**
   - 既存カードの文面修正や並び順変更を行う際は、**元のノートGUIDを必ず維持する**。GUIDを変更するとAnki側で新規カードとして重複登録されるため、勝手に再採番しない。
   - 完全に不要として削除するカードのGUIDのみ破棄する。
   - 一問一答と4択は別ノートとして独立したGUIDを持つことを確認する。

4. **旧ファイルの退避バックアップ**
   - 修正前の旧 `.txt` ファイルは削除する前に、リポジトリルートの `.local-history/` フォルダへ退避コピーする。

5. **新タイムスタンプファイルの出力**
   - 修正後のファイルは、生成時のローカル日時（`YYYYMMDD-HHmmss-fff`）を付けた新しいファイル名で `output/` に出力する。
   - 旧ファイルを `output/` から削除し、最新の成果物のみが `output/` に残るように整える。

## 完成時と検証要件

修正後のファイルを読み戻し、以下を必ず検証する：

- 先頭3行が `#separator:tab`、`#html:true`、`#guid column:1` であること。
- すべてのレコードがGUIDを含む物理3列であること。
- GUIDが全カード間で一意であり、Anki Base91形式であること。
- カード本文（表・裏）にGUIDや問題IDが混入していないこと。
- 一問一答と4択の間でカード総数が一致し、各行の設問テーマが1対1で整合していること。
